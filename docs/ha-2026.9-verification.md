## 2. The claim the whole plan rests on

`async_supports_streaming_input` is implemented exactly as the handoff says. Verbatim, from
`homeassistant/components/tts/entity.py:93-98`:

```python
    def async_supports_streaming_input(self) -> bool:
        """Return if the TTS engine supports streaming input."""
        return (
            self.__class__.async_stream_tts_audio
            is not TextToSpeechEntity.async_stream_tts_audio
        )
```

An identity comparison against the base function object. No flag, no registry, no manifest key.
Defining `async_stream_tts_audio` **is** the opt-in, and it opts in the moment the method exists.

Confirmed by running it, not just reading it. A subclass with no override returns `False`; a subclass
that defines the method returns `True`; and a subclass of that subclass also returns `True`, because
the attribute lookup walks the MRO and still does not land on the base function.

Three things follow, and the third is not in the handoff:

1. The decision to hold chapter 6 until chapter 5 runs on real hardware is correct and remains
   correct on 2026.9.2. A half-built socket path goes live the instant the method is defined.
2. The consumer is `homeassistant/components/tts/__init__.py:1106-1108`, which branches on
   `not engine_instance.async_supports_streaming_input()`. Assist pipelines and `tts.speak` both
   route through this one function, so there is no "streaming for Assist only" half-state. It is all
   or nothing, per entity.
3. The method is **not** `@final`. `internal_async_stream_tts_audio` at `:162` and
   `async_internal_get_tts_audio` at `:200` both are, so the omission is deliberate rather than an
   oversight. That gives chapter 6 an escape hatch the handoff does not mention: `async_stream_tts_audio`
   can be defined and shipped while `async_supports_streaming_input` returns `False`, gating streaming
   behind a config option. Worth knowing; not worth using without a reason, since the handoff's
   "it has to work" framing is the better default.

## 3. The WAV question

`custom_components/deepgram_tts/stream.py:39-43` bets the streaming path on ffmpeg reading to end of
stream when it sees an all-ones length sentinel. Nobody had checked. It is a good bet.

### What HA actually runs

`homeassistant/components/tts/__init__.py:326-360` builds an ffmpeg command line. Two lines matter,
`:331-335`:

```python
    command = [ffmpeg_manager.binary, "-hide_banner", "-loglevel", "error"]
    if from_extension:
        command.extend(["-f", from_extension])

    if is_input_gen and from_extension == "wav":
        # The container is known, so minimize probing latency for live TTS audio.
        command.extend(["-probesize", "32"])
```

`from_extension` is whatever the entity reported, passed as `-f`, which forces the demuxer rather
than letting ffmpeg probe. The second block is the tell: core HA has a special case whose only
purpose is live WAV TTS streams. The path we plan to use is a path core built for.

### The empirical answer

I replicated that command byte for byte against the installed ffmpeg (8.1.2), feeding a header plus
600 ms of PCM through a non-seekable pipe in 4 KB writes, exactly as
`homeassistant/components/tts/__init__.py:378-386` feeds it:

```
ffmpeg -hide_banner -loglevel error -f wav -probesize 32 -i pipe:0 -f mp3 -q:a 0 pipe:1
```

| Header | Result |
| --- | --- |
| `RIFF` size and `data` size both `0xFFFFFFFF` (ours) | exit 0, 5445 bytes out, no stderr |
| both zero, what `wave` writes and what core's own wyoming produces | exit 0, 5445 bytes out |
| honest sizes, only possible after buffering the whole clip | exit 0, 5445 bytes out |
| `RIFF` `0xFFFFFFFF`, `data` 0 | exit 0, 5445 bytes out |
| `RIFF` 0, `data` `0xFFFFFFFF` | exit 0, 5445 bytes out |

Identical output in all five cases. The length fields are ignored on a pipe. Decoding to raw
`s16le` returned 28800 bytes against 28800 fed in, so nothing is truncated at either end. The
44-byte header split across two separate writes also works, so `-probesize 32` does not require the
header to arrive in one piece.

**Verdict: CONFIRMED. `stream.py`'s sentinel is safe, and no change is needed.**

Two things the sentinel does not buy:

- **Raw PCM with `extension="wav"` and no header fails.** ffmpeg exits 183 with
  `invalid start code [192][224][192][224] in RIFF header`, produces zero bytes, and HA raises
  `HomeAssistantError` at `homeassistant/components/tts/__init__.py:406-413`. The header is not
  decoration. `stream.py:155` yields it before any frame, which is right.
- **The bytes can reach a media player unconverted.** When the caller asks for `preferred_format=wav`
  and nothing else, `needs_conversion` is `False` and our sentinel header is served verbatim. ffmpeg
  tolerance says nothing about what the player does with it. Untested here, and it needs a real
  device.

### Conversion does not cost us latency

If ffmpeg buffered to EOF, converting a stream to the default mp3 would delete the point of
streaming. It does not. Feeding 3 seconds of audio over 1.80 s of wall time, the first converted
output byte came back at 0.769 s. Progressive, comfortably ahead of the input finishing.

### But conversion is not optional, either

`homeassistant/components/tts/__init__.py:1068-1070`:

```python
        if ATTR_PREFERRED_FORMAT in supported_options:
            final_extension = options.get(ATTR_PREFERRED_FORMAT, _DEFAULT_FORMAT)
        else:
            final_extension = options.pop(ATTR_PREFERRED_FORMAT, _DEFAULT_FORMAT)
```

`_DEFAULT_FORMAT` is `"mp3"`. When nobody requests a format, `final_extension` is `"mp3"`, our
extension is `"wav"`, and `needs_conversion` at `:1151-1157` is `True`. The handoff's "returning WAV
and letting HA transcode is correct and free" is right about correct and wrong about free: an
ffmpeg subprocess per turn is the normal case, not the exception. On a Pi that is a real cost, and
it is still the right trade against transcoding ourselves.

Assist makes it unconditional. `homeassistant/components/assist_pipeline/pipeline.py:1425-1431`
sets `preferred_format`, `preferred_sample_rate`, `preferred_sample_channels`, and
`preferred_sample_bytes` together whenever a satellite wants wav, at 16000 Hz mono 16-bit
(`homeassistant/components/assist_pipeline/const.py:20-22`). A non-`None` sample rate alone forces
conversion, so even a wav-to-wav Assist turn goes through ffmpeg. Our
`WS_SAMPLE_RATE` is 24000, so every Assist turn also resamples 24k to 16k. Verified working:
`-ar 16000` on the sentinel header returned exit 0.

### The complete option set

From `homeassistant/components/tts/__init__.py:97-114`. Everything a TTS entity can advertise in
`supported_options`:

| Constant | Value | Line |
| --- | --- | --- |
| `ATTR_VOICE` | `voice` | 105 |
| `ATTR_AUDIO_OUTPUT` | `audio_output` | 98 |
| `ATTR_PREFERRED_FORMAT` | `preferred_format` | 99 |

`ATTR_PLATFORM` (`:97`) and `ATTR_MEDIA_PLAYER_ENTITY_ID` (`:104`) are service-call fields, not entity

Three notes on that set:

- **`ATTR_AUDIO_OUTPUT` is dead weight for us in 2026.9.2.** It is defined at `:98`, exported at
  `:73`, and referenced nowhere else in the `tts` component. `wyoming/tts.py:55` and
  `cloud/tts.py:351` advertise it and `cloud/tts.py:422, :441` read it, but each of those supplies
  its own default (`cloud/tts.py:337`); the TTS component never populates it, and no caller in the
  installed tree sends it. Our interface contract puts it in `supported_options` for chapter 5.
  Harmless, and it does nothing unless we give it a default and read it ourselves.
- **The five `preferred_*` options are always accepted** whether or not we advertise them,
  `homeassistant/components/tts/__init__.py:108-114` and `:835-837`. Advertising one changes only
  whether it is left in the options dict our entity receives (`.get`) or stripped out (`.pop`). It
  does not suppress the ffmpeg conversion either way.
- **Anything else not in `supported_options` is a hard error.** `homeassistant/components/tts/__init__.py:843`
  raises `HomeAssistantError(f"Invalid options found: {invalid_opts}")`. So `CONF_SPEED` must be in
  `supported_options` or a `tts.speak` carrying `speed` fails outright. The interface contract
  already has it.

## 4. `async_timeout`: right conclusion, wrong reason for the test suite

The handoff calls this claim load-bearing, and it is: the prior integration imported `async_timeout`
with `"requirements": []`, and on a real Home Assistant nothing installs it, so the integration
could not load.

That is confirmed for a real instance. `async_timeout` appears in none of the 48 `Requires-Dist`
lines in `homeassistant-2026.9.2.dist-info/METADATA:26-73`. Its only mention in
`homeassistant/package_constraints.txt` is a pin in the constraint section, `:211-213`:

```
# 5.0.0 breaks Timeout as a context manager
# TypeError: 'Timeout' object does not support the context manager protocol
async-timeout==4.0.3
```

A pin in that section applies *if* something else pulls the package in. It does not install it.

**But `async_timeout` 5.0.1 is installed in this venv and imports cleanly.** It arrives through
`ha_ffmpeg-3.2.2.dist-info/METADATA:23`, `Requires-Dist: async-timeout`, with no version marker,
unlike `aiohttp-3.14.3.dist-info/METADATA:36` which gates it behind `python_version < "3.11"`.

Consequences:

1. **Our test suite cannot catch the fork's bug.** An `import async_timeout` in
   `custom_components/` would pass all 62 tests and fail on a real instance. The rule in the
   interface contract ("`asyncio.timeout`, never `async_timeout`") is not enforced by anything that
   runs. `scripts/manifest_check.py` is the only thing standing between us and a repeat, so it needs
   to keep catching undeclared third-party imports.
2. The installed 5.0.1 violates HA's own `==4.0.3` constraint, because
   `pytest-homeassistant-custom-component` resolves dependencies without applying
   `package_constraints.txt`. Harmless as long as we never import it.

Our code does not believe the wrong version of this. `grep async_timeout custom_components/` returns
nothing, and `custom_components/deepgram_tts/stream.py` uses `asyncio.create_task` plus aiohttp's own
`timeout=` keyword throughout.

## 5. What we would have gotten wrong

Only the differences that could change our code. Everything else above is confirmation.

1. **Believing WAV output is free would have hidden an ffmpeg subprocess per turn.** `final_extension`
   defaults to `"mp3"` (`homeassistant/components/tts/__init__.py:1068-1070`), so returning `"wav"`
   means conversion runs on essentially every call rather than only when a caller asks for something
   else. The design decision does not change, because doing our own transcode is still worse, but any
   Pi latency budget written from the handoff's "correct and free" is wrong by one ffmpeg spawn per
   turn. **Does our code believe it?** Partly. `custom_components/deepgram_tts/stream.py:39-42`
   already names ffmpeg as the consumer, so the mechanism is understood, but neither the code nor
   `docs/superpowers/interface-contract.md` records that the conversion is unconditional.

2. **Trusting the test venv on `async_timeout` would let the fork's exact bug through.** It imports
   fine here because `ha-ffmpeg` drags it in. See section 4. **Does our code believe it?** No, the
   code is clean, but the enforcement story does: the interface contract treats "tests run with
   `.venv/bin/pytest`" as the safety net, and for this class of bug it is not one.

3. **`mutagen` is pinned to the wrong version and for the wrong reason.** Our
   `requirements-test.txt` pins `mutagen==1.47.0` with a comment saying it belongs to
   `homeassistant.components.tts`. That is right about the ownership and wrong about the version:
   `homeassistant/components/tts/manifest.json:11` and `homeassistant/package_constraints.txt:49`
   both say `1.48.1`. Low stakes, since `write_tags` only runs when the final extension is `"mp3"`
   (`homeassistant/components/tts/__init__.py:1028`) and never touches our bytes on the streaming
   path, but a test venv that disagrees with the target on a pinned version is a trap for later.
   **Does our code believe it?** Yes, `requirements-test.txt` is the wrong pin today.

4. **Treating the handoff's option list as complete would have missed `preferred_sample_channels`,
   `preferred_sample_bytes`, and `preferred_bitrate`.** Assist sends the first two on every wav turn
   (`homeassistant/components/assist_pipeline/pipeline.py:1428-1431`). They never raise, because
   `_PREFFERED_FORMAT_OPTIONS` at `homeassistant/components/tts/__init__.py:108-114` is always
   accepted, so this is a documentation gap rather than a defect. **Does our code believe it?** The
   interface contract's `supported_options` list is short, which is fine.

5. **`integration_type` and `iot_class` are validated by nothing we run.** There is no manifest
   schema and no hassfest in the wheel; `iot_class` is a bare `str` at
   `homeassistant/loader.py:267`. A typo in either key would load fine locally and fail only in the
   hassfest CI job. **Does our code believe it?** Our manifest is correct and matches `elevenlabs`
   field for field, so nothing to fix. Worth knowing that local testing proves nothing here.

Not a difference, but the near miss worth recording: **base language codes are safe.**
`homeassistant/components/tts/__init__.py:821` rejects a language by exact membership in
`supported_languages`, which reads like a trap for a list of base codes only. It is not, because
`homeassistant/components/assist_pipeline/pipeline.py:216-222` negotiates first through
`language_util.matches`. Verified: `matches("en-US", ["en"])` returns `["en"]`, and
`matches("es-419", ["es"])` returns `["es"]`. The pipeline then stores the negotiated `"en"`, which
is exactly what the membership check sees. Settled decision 4 in the handoff is correct, and the
"base codes only, never a mix" rule earns its place: `matches("en-US", ["en", "en-US"])` returns
`["en-US", "en"]` and the pipeline takes the first, so a mixed list makes the regional code win and
forces voice resolution to handle both spellings.

## 6. How a core integration actually streams

Three core integrations implement `async_stream_tts_audio` in 2026.9.2, found by grepping
`homeassistant/components/`: `elevenlabs/tts.py`, `wyoming/tts.py`, and `cloud/tts.py`. The handoff
names `elevenlabs` as the closest analog, which is right on the manifest and wrong on the code.
**`wyoming` is the reference implementation for chapter 6**, because it is the only one that streams
a WAV header followed by raw PCM, which is our exact problem.

### `wyoming`, the structural match

`homeassistant/components/wyoming/tts.py:191-219`. The shape is our shape: connect, spawn a
background task that forwards text, return a `TTSAudioResponse` whose generator reads audio.

```python
        client = AsyncTcpClient(self.service.host, self.service.port)
        await client.connect()

        # Stream text chunks to client
        self.config_entry.async_create_background_task(
            self.hass,
            self._write_tts_message(request.message_gen, client, voice),
            "wyoming tts write",
        )

        async def data_gen():
            # Stream audio bytes from client
            try:
                async for data_chunk in self._read_tts_audio(client):
                    yield data_chunk
            finally:
                await client.disconnect()

        return tts.TTSAudioResponse("wav", data_gen())
```

Four differences from `custom_components/deepgram_tts/stream.py`, in descending order of how much
they matter.

**1. The unknown length is written as zero, not as all ones.**
`homeassistant/components/wyoming/tts.py:248-252`:

```python
    async def _read_tts_audio(self, client: AsyncTcpClient) -> AsyncGenerator[bytes]:
        """Read audio events from the client and yield WAV audio chunks.

        The WAV header is sent first with a frame count of 0 to indicate that
        we're streaming and don't know the number of frames ahead of time.
        """
```

It builds the header with Python's `wave` module and closes it having written no frames
(`:269-277`), which produces `RIFF` size 36 and `data` size 0. We hand-pack `0xFFFFFFFF` into both
(`custom_components/deepgram_tts/stream.py:43`). Section 3 shows both decode identically through
HA's ffmpeg command, so this is not a bug, but core's answer is the zero and ours is the sentinel.
If a media player ever receives our bytes unconverted and chokes, switching to zeros is the first
thing to try, and it costs nothing.

**2. Lifetime is tied to the config entry, not to a bare task.** Wyoming uses
`self.config_entry.async_create_background_task` (`:205-209`) and `elevenlabs` uses
`self.hass.async_create_background_task` (`:231-233`). Both are tracked by HA and cancelled on
unload or shutdown. `custom_components/deepgram_tts/stream.py:160` uses a raw
`asyncio.create_task`. `FluxSocket` awaits it in a `finally` (`:165`, `:242-260`) so it is not
leaked, and `stream.py` is deliberately written to be testable without a `hass` around it, so this
is defensible. But whatever owns `FluxSocket` in chapter 6 should register the turn against the
config entry, or an unload mid-turn leaves an in-flight socket behind.

**3. `elevenlabs` does split sentences, and that is not a counterexample.**
`homeassistant/components/elevenlabs/tts.py:184, 207-233` runs a
`sentence_stream.SentenceBoundaryDetector` over the incoming chunks and synthesizes on sentence
boundaries, on a schedule of 1 then 3 then everything (`:239`). The handoff's rule against sentence
splitting still stands for us: ElevenLabs exposes request/response HTTP per text, so the client has
to decide the boundaries, while Flux is a socket that places flush boundaries server-side. The
useful fact is that `sentence-stream==1.3.0` is installed
(`sentence_stream-1.3.0.dist-info`) and is HA-blessed, so if the socket ever turns out to need
help, there is a core-sanctioned tool rather than a regex.

**4. Wyoming swallows disconnects; we raise.** `homeassistant/components/wyoming/tts.py:283-285`
catches `OSError` and `WyomingError`, logs a warning, and ends the generator, yielding truncated
audio. `elevenlabs/tts.py:304-311` raises `HomeAssistantError` from inside the generator. Ours
raises `DeepgramConnectionError` from `_receive` (`custom_components/deepgram_tts/stream.py:236-240`)
specifically so chapter 6 can fall back to batch. That is the better design, and section 7 is the
constraint it has to respect.

`cloud/tts.py:443-465` is the third and is the least useful: it hands `request.message_gen` straight
to `self.cloud.voice.process_tts_stream` and returns `TTSAudioResponse(AudioOutput.WAV.value, data_gen)`.
One fact worth taking from it: it also reports `"wav"` from the streaming path. Two of the three core
streaming integrations return WAV, so settled decision 6 is the core-normal choice, not an odd one.

## 7. What the installed TTS component does that section 4 never mentions

Five things, all in `homeassistant/components/tts/__init__.py`, that a custom integration author
would want before writing chapter 6.

**1. Our generator is drained once, by a background task, whether or not anyone listens.**
`TTSCache.async_load_data` at `:160-183` iterates `self._data_gen` exactly once, appending to
`_partial_data` and fanning each chunk out to per-consumer queues. `async_stream_data` at `:185-220`
replays the buffer and then follows the queue. The drain is kicked off as a background task the
moment the stream is created (`:928-933`, `:986-990`). So the socket opens and Deepgram characters
are billed as soon as HA creates the result stream, even if the media player never connects.

**2. A fallback that raises after yielding is worse than no fallback.** `:1009-1018` catches
everything from the drain, logs `Error getting audio for %s`, pops the cache entry, and returns.
The error is stored and re-raised to consumers, but `:207-211` yields every chunk buffered *before*
the failure first. A mid-turn socket death therefore delivers truncated audio followed by an
exception. Concretely, for chapter 6: if `tts.py` catches `DeepgramConnectionError` from
`FluxSocket.stream` after frames have already been yielded and then yields a batch result, the
consumer receives a truncated WAV stream concatenated with a second complete audio file. **The
batch fallback is only safe before the first yield.** After that, the honest options are to let it
truncate or to buffer the first frames, and buffering reintroduces the latency streaming exists to
remove. This is the sharpest edge in chapter 6 and the handoff does not mention it.

**3. Streamed audio is never cached and never deduplicated.** `:930` passes `store_to_disk=False`
for the streaming-input path, and `:916` keys the cache on `ulid_util.ulid_now()` rather than a
message hash. The batch path keys on a SHA-1 of the message (`:952-956`) and does write to disk.
Two identical Assist responses re-synthesize over the socket, every time. That is a cost argument
for chapter 6 and a reason to keep chapter 5's batch path as more than a fallback.

**4. `mutagen` only ever touches mp3.** `:1028` guards `write_tags` on `cache.extension == "mp3"`,
and `cache.extension` is the *final* extension, not what our entity returned. Our bytes never reach
mutagen on the streaming path. It stays out of `manifest.json` requirements, as
`requirements-test.txt` already says.

**5. Overriding the four `cached_property` members with a plain `@property` is fine.**
`custom_components/deepgram_tts/tts.py:44-52` does this for `default_language` and
`supported_languages`, and so does core's `google_cloud/tts.py:142-155` for all four. The only trap
in `CachedProperties` is at `homeassistant/helpers/entity.py:380-383`, which raises
`TypeError(f"Can't override {attr_name} in subclass")` if a subclass defines `_attr_<name>` as a
function or a property. Setting `_attr_supported_languages` to a plain list, or overriding the
property itself, are both safe. The only cost of a plain `@property` is that the value is rebuilt on
every read, and `supported_languages` is read on every option validation (`:821`). Once chapter 3
builds that list from the merged catalog, `_attr_supported_languages` set once in `__init__` is
cheaper than a property that rebuilds it.
