The integration, with pictures

Deepgram Flux TTS as the voice of a Home Assistant voice assistant. One picture per mechanism, no code required to follow it.

1. Where this integration sits

Six things have to work for a voice assistant to answer out loud, and this project is one of them. It does not hear you, it does not transcribe you, and it does not decide what to say. It turns reply text into audio bytes and hands them back. Every bug in the old integration lived inside that one box.

2. Two endpoints, one client

The prefix is the entire routing rule. One synthesize method, two URLs, no configuration and no lookup table.

Parameter validation runs before the auth check, which is why every endpoint fact in the handoff was enumerated without a working API key. It also means a routing mistake fails loudly and cheaply rather than silently returning the wrong voice.

3. Two catalogs, one voice list

Two fetches, no auth on either, merged once at setup. The family tag is what lets a single voice picker show both without the user needing to know there are two APIs underneath.

5. The hyphen

Splitting "en-US" on an underscore finds no underscore, so it hands back the whole string. Nothing raises. The only way you find out is by opening the dropdown and seeing en and en-US sitting next to each other as if they were different languages.

6. Batch and streaming, on the same clock

Moving version, with a playhead sweeping the axis: assets/streaming-vs-batch.svg

Same reply, same voice, same audio in the end. The difference is not architecture, it is 1.35 seconds of silence in a room where someone just asked a question. Every audio frame for a turn arrives between SpeechStarted and SpeechMetadata, and the first one lands before the sentence is finished.

7. The server places the flush boundaries

This is the single most important fact in the handoff, and it is a deletion rather than a feature. A regex over the reply text means this paragraph was not read.

8. The trap: there is no streaming flag

This is the diagram to remember if you are writing any Home Assistant TTS entity. The bottom row is the one people actually use and the top row is the one they test, so a broken socket path looks like a working integration right up until someone talks to it.

9. Two entries, side by side

Two entries is not a nice-to-have here. Because every Flux voice is English, an English and a Spanish household needs two entities, which means single_config_entry stays out of the manifest and no constant unique_id stands in for it.

10. The order it gets built in

The whole thing in one breath

A model id's prefix picks the endpoint, and nothing else does. Two public catalogs merge into one voice list, which is the only way Flux becomes visible at all. Every Flux voice is English, so Aura-2 is the only exit for a Spanish pipeline, and that is why two config entries have to be allowed. Tokens stream straight into one socket and the server decides where to breathe, which is a 206-line file that does not get written. And defining async_stream_tts_audio turns streaming on with no flag, so the half-built version of it is the version every Assist reply uses.
