ha-deepgram-tts: state of the fork

Audit of the forked alceasan/ha-deepgram-tts integration, September 15 2026. Last upstream commit: January 12 2026 (8 months cold). Scope: will it still run on current Home Assistant, and what does moving to Flux TTS actually take.

Verdict

It will almost certainly not load on a current Home Assistant, and even if it loads, the streaming path that Assist prefers is guaranteed to fail. Both failures come from the same root cause: the integration declares "requirements": [] in its manifest while importing two packages it does not own.

The important part: because async_stream_tts_audio is overridden, HA auto-detects streaming support (async_supports_streaming_input compares the subclass method against the base method) and routes Assist pipeline responses down the broken path. So the failure mode is not "streaming is a bit worse." It is "voice assistant responses raise, one-shot service calls work."

Code findings

Blockers

  1. Undeclared runtime dependencies. manifest.json has "requirements": [] while the code imports async_timeout and pydub. Fix by deleting both: async_timeout.timeout(n) becomes asyncio.timeout(n) (stdlib since 3.11), and pydub goes away entirely once the streaming rewrite lands.
  2. Setup failure is not retryable. async_setup_entry awaits models_client.fetch_models() and lets a raw aiohttp error escape. That marks the entry failed with no retry. It should raise ConfigEntryNotReady, which is exactly the case this exception exists for.
  3. Streaming does not stream. tts.py builds a message_gen() that accumulates every chunk from request.message_gen into one string, then yields it once. The whole LLM response is buffered before the first synthesis call, which deletes the entire latency benefit of the 2025.7 streaming API that the README advertises.

Correctness and cost

  1. Request body may be wrong. api.py sends Content-Type: text/plain with a raw UTF-8 body. The /v1/speak reference specifies application/json with {"text": "..."}. This is a plausible cause of the "400 Bad Request" the 1.0.1 changelog claims to have fixed by other means. Unverified: auth is checked before body parsing, so it cannot be probed without a real key.
  2. Decode then re-encode for nothing. async_process_stream takes each MP3 fragment from Deepgram, decodes it with pydub, and re-exports it as MP3 before yielding. That is a full transcode per sentence on a Raspberry Pi for zero benefit. HA already runs ffmpeg conversion in _async_convert_audio when the requested preferred_format differs from what the entity returns.
  3. Buffer threshold explodes. min_len = 2 ** count * 10 in _sentence_generator, where count increments per input chunk. By chunk 20 the threshold is 10 megabytes. It happens to be harmless today only because message_gen() yields exactly one chunk.
  4. Sentence splitter is naive. _find_sentence splits on (?<!\d)[.!?], so "Dr." and "3 p.m." each become a separate synthesis request, each with its own network round trip and its own audio boundary click.
  5. Single-instance lock. async_set_unique_id("deepgram_tts") is a hardcoded constant, so you can never configure a second entry, for example one entity on Flux and one on Aura-2 for comparison.

Polish and hygiene

  1. Leftover blueprint scaffolding. api.py defines _verify_response_or_raise twice (the second silently wins) plus three dead IntegrationBlueprintApiClient* exception classes. const.py and __init__.py docstrings still describe integration_blueprint.
  2. No translations. No strings.json and no translations/, so the config and options flows show bare step ids with no labels or descriptions.
  3. Private attribute poking. __init__.py sets client._models_cache from outside the class, and tts.py reads it back through getattr and through self._processor._client._models_cache. Make it a constructor argument.
  4. Options flow __init__ is dead weight. DeepgramTTSOptionsFlowHandler.__init__ accepts config_entry and does pass. This accidentally dodges the 2025.12 breaking change (which fires when you assign self.config_entry), but delete the override anyway so the intent is clear.
  5. Unused imports and mixed-language comments. timedelta and DeepgramTtsEntity in __init__.py, re in tts.py, slugify in config_flow.py. Roughly a dozen Spanish inline comments throughout, which is fine to keep but worth normalizing if this becomes your fork.

Metadata that still points upstream

manifest.json lists @alceasan as codeowner and github.com/alceasan/ha-deepgram-tts/issues as the issue tracker. The README's HACS instructions have a typo (alceasan/ha-deemgram-tts). The CHANGELOG dates do not match the git history: 1.0.2 is dated 2026-08-01 but was committed 2026-01-08, and 1.0.1 is dated 2025-01-10 but was committed 2025-10-01.

Moving to Flux TTS

This is a bigger change than swapping a model string. Flux TTS is a different endpoint with a different protocol, and the two families do not mix.

The one real regression

Every Flux voice is English (en, en-US). Aura-2 covers seven languages (en, es, de, fr, nl, it, ja). If you go Flux-only, supported_languages collapses to ["en"] and any non-English Assist pipeline loses its voice. That argues for keeping both families and routing on the model prefix rather than replacing Aura outright.

Why the WebSocket path is the actual prize

Flux TTS maps onto HA's streaming TTS API almost one to one, and in doing so deletes most of this repo's complexity.

Client messages: Speak ({"type":"Speak","text":"..."}), Flush, Interrupt (with an optional playback_offset), Configure (speed, 0.5 to 1.5 in 0.05 steps), Close.

Server messages: Connected, SpeechStarted, SpeechMetadata, SpeechInterrupted, Flushed, SessionMetadata, ConfigureSuccess, ConfigureFailure, Warning, Error. Every audio frame for a turn arrives between SpeechStarted and SpeechMetadata.

So async_stream_tts_audio becomes: open the socket, forward each chunk of request.message_gen as a Speak, send Flush when the generator is exhausted, and yield binary frames until SpeechMetadata arrives. The server decides where the flush boundaries go, which means stream_processor.py deletes entirely: no sentence regex, no pydub, no MP3 fragment concatenation, no 150 ms synthesis delay, no per-sentence round trips. That file is 206 lines of workaround for a problem the v2 API does not have.

Two mechanical details worth settling before you write code. First, the socket returns raw PCM with no container, so the entity should either prepend a WAV header and report extension="wav", or advertise ATTR_PREFERRED_FORMAT in supported_options and let HA's ffmpeg conversion handle it. Second, SpeechInterrupted carries text_spoken and text_remaining, which is the right primitive for Assist barge-in, but HA's TTS entity API has no barge-in hook today. Treat it as a later win, not a day-one requirement.

Engineering note on voice choice, not a gate: flux-marcus-en and flux-brittany-en drift in pitch and volume between calls, sometimes emit an audible musical note before a greeting, and can click at clip starts. Relevant only if you pick one as the shipped default, since a home assistant makes many short separate calls and the drift is most audible exactly there.

Recommended order of work

Phase 0: unbreak it (about 30 minutes)

  1. Replace async_timeout.timeout() with asyncio.timeout() in api.py and api_models.py.
  2. Delete the pydub import and _trim_end_of_audio, and stop re-encoding in async_process_stream. Pass fragments through untouched.
  3. Wrap the fetch_models() call in async_setup_entry and raise ConfigEntryNotReady.
  4. Switch /v1/speak to application/json with a {"text": ...} body.
  5. Bump hacs.json to a current minimum, retarget codeowner and issue tracker at your fork, and cut a v1.1.0 tag so HACS has a release.

After this it should load and both paths should work. This is the point to install on your instance and confirm before building anything new.

Phase 1: Flux on the batch endpoint (2 to 3 hours)

  1. Merge the two catalogs: /v1/models for Aura, /v2/models for Flux, into one voice list.
  2. Route by model prefix in the API client: flux-* to /v2/speak, everything else to /v1/speak.
  3. Use metadata.display_name for the Voice label instead of name, which is the bare lowercase given name.
  4. Add a speed option, since Flux exposes it and Aura does not.
  5. Add async_migrate_entry and bump the config flow VERSION, because the stored voice id shape is about to change.

Phase 2: the WebSocket rewrite (4 to 6 hours)

  1. Implement the socket client against the Speak / Flush / SpeechStarted / SpeechMetadata lifecycle.
  2. Rewrite async_stream_tts_audio to forward request.message_gen chunk by chunk instead of buffering it.
  3. Delete stream_processor.py.
  4. Settle the container question: WAV header plus extension="wav", or ATTR_PREFERRED_FORMAT passthrough.
  5. Fall back to the batch endpoint when the socket fails, so a dropped connection degrades instead of erroring.

Phase 3: hygiene (1 to 2 hours)

  1. Add strings.json and translations/en.json.
  2. Strip the blueprint leftovers, the duplicate function, and the unused imports.
  3. Add a tests/ directory with current pytest-homeassistant-custom-component, and move dev tooling to ruff.
  4. Add the missing devcontainer Dockerfile or drop .devcontainer.json.
  5. Rewrite README and CHANGELOG against your fork, and fix the dates.

What I could not verify

  • No live synthesis. There is no Deepgram API key on this machine, so nothing past the auth check was exercised. Every endpoint fact above comes from unauthenticated probes (which do return real parameter validation errors) plus the docs.
  • Whether /v1/speak rejects text/plain. Auth is validated before the body, so a dummy key always returns 401 regardless of content type.
  • Whether async_timeout happens to be present on your instance. It is absent from HA core requirements, but another custom integration could have pulled it in transitively. Worth one command before assuming the diagnosis.

How to confirm on your instance

Three checks, in order, before writing any code:

  1. In the HA container or venv, run python -c "import async_timeout" and python -c "import pydub". Two failures confirms both blockers.
  2. Install the fork as-is, restart, and read the log for ModuleNotFoundError during setup of deepgram_tts.
  3. If it does load, call tts.speak once directly (should work), then trigger the same text through an Assist pipeline (should raise the pydub RuntimeError). That split is the signature of this specific breakage.
