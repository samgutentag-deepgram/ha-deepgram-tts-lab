Moving Deepgram Flux TTS to the real Home Assistant

Written 2026-09-16 · main at ece0621, 53 commits, 122 tests · chapter-6-streaming at 1a08e6a, 5 commits ahead, 132 tests

This is the plan for taking what runs on the Mac tonight and putting it on the Raspberry Pi, then onto HACS. It is written to be picked up cold after a gap, so it restates what is already true rather than assuming you remember.

Where this actually is

The integration works. On 2026-09-16 a real Home Assistant 2026.9.2 ran on the Mac with this code installed, the real config flow created a real entry, and it spoke out loud in all seven supported languages with the right voice family for each, then played through the Sonos Beam in the living room. That is not a unit test result, it is audio a person heard.

What is verified, with the evidence in .hub/assets/:

  • Authenticated round trips against /v2/speak and /v1/speak
  • Config flow end to end, including a rejected key mapping to invalid_auth
  • Seven languages, each resolving to the correct voice family, pt correctly refused
  • Settled decision 4 on a live instance: zero Flux leaks for non-English
  • The Flux websocket: 24 kHz confirmed, WAV decodable by ffmpeg, 99 ms to first audio
  • An expired key on the socket reported as auth, not as a dead network
  • Playback through a Sonos Beam, including a stream with no Content-Length
  • HACS distribution rules: 22 verified, 0 failures, brand assets already exist

What is not verified is everything about the Pi, and one thing about Assist. No line of this has run on ARM, on that instance, or through a real Assist pipeline. That last one matters more than it sounds and is step 4 below.

Step 1. Get the code onto the Pi

The situation, so you do not rediscover it

Probed 2026-09-15: homeassistant.local is 192.168.1.197, port 8123 answers and /api/ returns 401, and ports 22, 22222, 445 and 139 are all refused. There is no SSH app and no Samba. File Editor and Studio Code Server are browser based: they can create a file and cannot receive one from the laptop. So deploy.sh has nowhere to connect, which is why HA_DEPLOY_TRANSPORT is deliberately blank in .env.sample.

The Pi can still reach the laptop, which is what the copy path uses.

set -a && source .env && set +a
./scripts/serve_bundle.sh

It tars the integration, serves it on the LAN for exactly one download, prints the single line to paste into the Studio Code Server terminal, and shuts the server down afterward. Verified over the real LAN address: twelve files, all byte-identical after extraction.

Then restart Home Assistant. Developer tools, YAML tab, Restart. This is not optional: sys.modules caches the import, so Python that Home Assistant has already loaded does not change without a restart. reload_config_entry re-runs setup against the module already in memory and will not pick up a single line of this.

If you would rather have a fast loop, install the Advanced SSH and Web Terminal app first. Then HA_DEPLOY_TRANSPORT=rsync in .env is a one word change and every other value in there is already correct: host, user root, port 22, config dir /config. You still restart every time, but the copy becomes instant.

Step 2. Configure it

Settings, Devices and services, Add integration, Deepgram TTS. Paste the key from .env. The voice step shows 138 voices with flux-haley-en preselected; accept it.

The entity will be tts.deepgram_flux_haley, titled Deepgram Flux (Haley).

Wait for the entity before concluding anything. Home Assistant answers /api/ long before it finishes setting up config entries, and a TTS call in that window returns Provider not found and looks exactly like a broken integration. The entry even reports state: not_loaded with reason: None during it. The readiness signal is the entity existing.

Step 3. Point it at the Sonos and make a sound

The Sonos integration is first party and discovers over SSDP with no configuration. The Beam is already known to work. Developer tools, Actions, tts.speak:

action: tts.speak
target:
  entity_id: tts.deepgram_flux_haley
data:
  media_player_entity_id: media_player.sonos_beam
  cache: false
  message: The back door has been unlocked since four this afternoon.

Do not verify this from the media player state. Home Assistant plays Sonos announcements as an audio clip overlay via loadAudioClip on the Sonos websocket, which never touches transport state. The speaker will say the words while the entity still reads idle. Verify by ear, or from the log with homeassistant.components.sonos at debug, where the line reads Playing ... using websocket audioclip.

cache: false matters on every test call. The TTS manager keys its cache on message plus language plus options plus engine, so a repeated message replays the first result and never reaches the integration at all.

Step 4. The tests that have to pass before HACS

docs/chapter-5-notes.md has the full eleven item hand-check list with paste-ready YAML. These four are the ones that are not covered by anything that has already run.

The four that matter

  1. A real Assist pipeline, end to end. Everything so far went through tts.speak and tts_get_url. Assist uses the streaming path, which is the one with the trap in it, and it is what every HACS user will actually exercise. Settings, Voice assistants, set the TTS engine to Deepgram, then talk to it. On main this exercises the batch path because streaming is off; that is still worth doing, because it proves the pipeline wiring independently of chapter 6.
  2. Streaming through the Sonos audio clip path. Untested and genuinely unknown. loadAudioClip hands Sonos a streamUrl and Sonos fetches it itself. Whether it starts on the first bytes or waits for the whole clip decides whether streaming is audible at all through a Sonos. If it buffers, the first-frame number never reaches a listener and the demo needs different hardware.
  3. The options flow. Change the voice, change the speed, confirm the entry reloads and the next call uses the new value. Unit tested only. Also confirm the speed slider does not offer off-grid values: the API rejects anything not on a 0.05 step.
  4. Two entries side by side. One Flux for English, one Aura for Spanish. Confirm they get distinct entity ids with no _2 suffix. Unit tested only, and it is the one design decision with no live evidence behind it.

Step 5. Decide on chapter 6

chapter-6-streaming is five commits ahead of main and adds streaming. It is written, it has 132 passing tests, and it has been exercised against the live API and through a real Home Assistant. It is not merged, on purpose.

Defining async_stream_tts_audio is itself the opt-in. Home Assistant detects streaming by comparing the class method against the base method. There is no flag. The moment that method exists, every Assist response in the house routes down the websocket while direct tts.speak calls keep working and hide any breakage. That is exactly how the community integration this replaces shipped broken.

The merge is one command once step 4 items 1 and 2 pass:

git checkout main && git merge chapter-6-streaming

What you get for it, measured rather than claimed: first audio in 99 ms against a 73 ms network floor, versus 3394 ms for batch to synthesize and transfer the whole clip. And one thing to know before writing about it: Flux emits on a sentence boundary, so a multi-sentence response starts speaking while the model is still generating, and a single-sentence one does not start until the text is complete.

Step 6. The flip, which is the real HACS prerequisite

This is a decision, not a step

HACS requires a public repository. This is a private lab repo, and by the convention in ~/LABS/CLAUDE.md the flip to public is one way and terminal:

  • History is rewritten into build order first, so the public commit log reads as a tutorial. The seven chapter structure was built to make that close to a no-op, but deciding the chapters is judgment, not tooling. Budget an hour.
  • .hub/ and advocacy/ are stripped from every commit, not just the tip. A .gitignore line does not do this.
  • After the flip the public repo is the repo of record. The lab repo is never worked in again except to write content from its ledger, and is never deleted.
  • Pull requests on the public repo are applied by hand here and arrive in a later snapshot. Nothing merges back.

Flip target: samgutentag-deepgram/ha-deepgram-tts, which does not exist yet. manifest.json already points documentation and issue_tracker at it, so those URLs 404 until it does. scripts/hacs_check.py knows this and reports them as skips rather than failures until hub.yml gains a public_repo key.

Do not do this in a hurry. It is the one action in this project with no undo.

Step 7. HACS, in two stages

Stage one, which is fast: custom repository

The moment the public repo exists, anyone can install this by adding the URL to HACS as a custom repository of type integration. No review queue, no waiting. This is the "sooner rather than later" path and it is the one to aim at first.

It needs a published GitHub release, not just a tag. .github/workflows/release.yml builds it and refuses when the tag disagrees with the version in manifest.json, which is 0.1.0 today.

Stage two, slower: the default store

A pull request to hacs/default, which is a review queue on someone else's repo. docs/hacs-submission.md has the full checklist. Current state from scripts/hacs_check.py: 22 verified, 8 unverifiable from here, 0 failures. All eight are GitHub side and unblock with the flip: public repo, description, topics, a published release, HACS having fetched it once, and the two Docker actions passing.

Brand assets are already done and not by us. home-assistant/brands has a custom_integrations/deepgram_tts/ entry with all four PNGs and the CDN serves them. They key on the integration domain, not the repository, and ours matches the community integration's. That removes the only requirement needing an asset nobody had made, and it is a hard reason never to rename the domain.

The shortest honest path

  1. Copy to the Pi, restart, add the integration, hear it on the Beam. one evening
  2. Work the four tests in step 4. one evening
  3. Merge chapter 6 if items 1 and 2 passed. one command
  4. Tag v0.1.0 and let the release workflow build it. minutes
  5. Do the flip, deliberately, with an hour set aside. one sitting, no undo
  6. Install it on your own instance from HACS as a custom repository, to prove the distribution path on a clean install. minutes
  7. Only then consider the hacs/default pull request.

Steps 1 through 4 are reversible and cheap. Step 5 is not. Everything after it is waiting on other people.
