Deepgram Flux TTS for Home Assistant

Session summary · 2026-09-15 · branch main at 42 commits · 120 tests green against real Home Assistant 2026.9.2

A Home Assistant custom integration that makes Deepgram Flux TTS the voice of a Home Assistant voice assistant now exists, installs, picks a voice out of a 138 voice catalog, and synthesizes. It has never spoken out loud, because there is no Deepgram API key on this machine and there is no speaker in your house. Those are the two things that stand between this and a demo, and neither is a code problem.

Five things only you can do

  1. Put a Deepgram API key in the environment. One key unblocks three separate things, including the only number the whole campaign rests on.
  2. Order hardware. Longest lead item in the project, and it is the first thing to start because everything visual waits on it. The recommendation is two Voice Preview Edition pucks at $58.95 each plus a $42.74 powered speaker. Full bill of materials in docs/hardware-bom.html.
  3. Answer three questions about your Home Assistant instance: install type, hostname, and which apps are installed. Listed verbatim in docs/deploy-notes.md. Thirty seconds to answer, an hour to guess wrong.
  4. Say go on the Asana project. project-hub init creates a team visible project plus four tasks, one of which needs a check-back date only you can pick. It was not worth guessing while you were out. Everything else in .hub/ is done and works without it.
  5. Nothing on advocacy intake. That is not waiting on a decision, it is waiting on chapter 5 making a sound. Every fact, angle, outline, draft and script is staged in advocacy/prep/ so intake is a short job instead of a cold start.

Where the code is

Chapter 6 is held for an engineering reason, not a procedural one. Home Assistant decides whether an integration streams by checking whether the class defines one method. Defining it is the opt-in. There is no flag, no config option, and no way to ship it half-built.

So main stops at a complete batch integration that is safe to install on your real instance today, and chapter 6 waits on a branch behind a measured latency number. Chapter 5's test suite asserts that streaming is off, so the assertion failing is the signal that the merge is a deliberate act rather than a side effect.

The hardware, which was the gap nobody had researched

Home Assistant is about physical devices, and a text to speech integration with nothing to play audio out of is a unit test. You own zero speakers and zero microphones today, so this was researched from scratch with current prices and buy links.

Two findings changed the recommendation. rhasspy/wyoming-satellite is archived and read only, last push January, 212 open issues abandoned, and every "build a Pi voice satellite" tutorial on the internet still points at it. That deleted the Raspberry Pi tier. And an ESPHome voice satellite advertising the speaker flag hard-refuses anything that is not WAV, which means a design decision made for software reasons turned out to be the only one the hardware accepts.

The five findings worth reading the ledger for

.hub/ledger.md has 48 entries. These are the ones that will end up in a post.

1. We shipped the exact bug we founded the project on avoiding

The handoff's first and heaviest rule: never let a broad handler turn your own auth error into something else, because then a caller cannot tell an expired key from a dead network. Every error path in the API client honors it. And then the websocket client did it anyway, because a rejected key fails the HTTP upgrade, which arrives as a connection error class, not as an authentication error. An adversarial review found it. The rule was written down, understood, and broken in the one place where the failure arrives through a transport nobody was picturing.

2. Two things with prose explaining why they mattered had no test at all

Mutation testing planted 15 defects and the suite caught 13. The two it missed both had ledger entries behind them. Deleting the guard that keeps a Spanish pipeline off an English voice left every test passing, because the fixture gave each language exactly one voice, so two different behaviors produced the same answer. A test whose fixture makes the right and wrong implementations agree is not a test, and it reads exactly like one.

3. The handoff's headline claim about the old integration was wrong

It said an undeclared async_timeout import meant the community integration "almost certainly did not load at all." It almost certainly did load: ha-ffmpeg requires async-timeout with no version marker, and the TTS component depends on ffmpeg. The pydub half stands and is the real cause, which makes the actual bug more interesting than the one we thought we had. Six handoff claims have been corrected, in docs/handoff-corrections.md. The handoff itself was not edited, on purpose.

4. A display name that is good enough to show is not good enough to identify

display_name is null, not missing, on 61 of the 102 Aura voices, so the obvious membership check does nothing and the fallback is the normal path. Then the fallback turned out to collide: two different live voices both render as "Asteria", same family, same accent. The voice picker labels carry the model id for that reason.

5. Entity IDs that read correctly next to a service that was dead

Chapter 1 set a naming attribute combination that produced exactly the entity IDs its own tests asserted, and made every synthesis fail with "TTS engine name is not set". The entity ID and the entity name come from different places, so a registry that looks right tells you nothing about whether the thing works. That is the second failure in this project that only the calling path surfaces, which makes it a pattern rather than a coincidence.

The strongest angle available today is not "Flux is fast." No latency has been measured, so that claim cannot be written. What is fully supported right now needs no hardware at all: the streaming opt-in trap, which any Home Assistant TTS author can fall into, and which we demonstrably fell into ourselves two hours after writing it down as a thing to avoid.

One editorial risk, named early because it gets worse the longer it goes unnamed. The audit material is about a volunteer's open source project, and roughly fifteen named defects with line numbers is accurate and could still read as dunking. The framing has to be transferable lessons, and the credit has to be real. It is in angles.md with four concrete failure modes and one test every sentence has to pass.
