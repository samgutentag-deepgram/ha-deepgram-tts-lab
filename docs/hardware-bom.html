2. How audio actually leaves the integration

You cannot pick hardware without this part, because the choice of playback device decides whether the streaming work in chapter 6 is visible or invisible.

The TTS entity never touches a speaker

Our entity returns bytes. That is the whole contract. What turns bytes into sound is a chain with an HTTP hop in the middle. Read from homeassistant/components/tts/__init__.py on the dev branch on 2026-09-15:

  1. Something asks for speech: an Assist pipeline run, or a tts.speak call, or assist_satellite.announce.
  2. HA's SpeechManager creates a ResultStream with a random token and hands back two identifiers: a media source id, and a URL, /api/tts_proxy/{token}.
  3. The caller targets a media_player. HA calls play_media on it with the media source id, which resolves to that proxy URL.
  4. The player fetches the URL over plain HTTP. The view serving it is TextToSpeechView, and it is marked requires_auth = False, so anything on the LAN that can reach HA can fetch it.
  5. Our generator is drained into that response as it produces bytes.

Step five is the one that matters. The proxy is an aiohttp StreamResponse. It calls prepare() when the first chunk arrives, write() per chunk, and write_eof() at the end. There is no Content-Length and no byte range support. Home Assistant is doing chunked transfer on purpose: our first audio frame can be on the wire before Deepgram has finished the sentence.

Whether that survives is entirely up to the thing on the other end of the socket.

There is a HEAD handler on that same view, and the comment above it says it exists because "some DLNA renderers, like Samsung ones" send HEAD before GET. It answers with a content type and no length. That comment is a map of where this design leaks: players that want to know the size before they start.

A media player is not a voice satellite

Two different entity types, and confusing them is the classic first-day mistake.

media_playerassist_satellite
JobPlay a URLRun a whole pipeline: wake word, speech to text, conversation, speech back
Stateplaying, paused, idleidle, listening, processing, responding
Speaks viatts.speak with media_player_entity_idassist_satellite.announce
Has a micNoYes, that is the point

A Voice PE registers as an assist_satellite and exposes a companion media_player. Firing tts.speak at that companion player can flip its state to playing and produce no sound at all, because the audio never enters the satellite's announcement path. The fix is assist_satellite.announce targeting the satellite. The clearest public write-up of that trap is a dev.to post from June 2024, which is old and is one person's experience, so treat the post as weak, but the code path in homeassistant/components/esphome/assist_satellite.py is consistent with it.

The two ways audio reaches an ESPHome satellite

This is the most useful thing I found, and it is verifiable in core today. ESPHome satellites split on a feature flag, and the two halves want different audio formats from us.

PathWhenWhat happens
HA pushes PCM Device advertises the SPEAKER feature. Old-style satellites, for example the Atom Echo. HA reads our stream itself and pushes it to the device over the ESPHome API or UDP at 16 kHz, 16-bit, mono, 512 samples per chunk. It refuses anything that is not WAV: if tts_result.extension != "wav" logs "Only WAV audio can be streamed" and gives up. It paces the send against a ring buffer on the device that the code's own comment says is "fixed at 512ms", held at "around 384ms (75% full)".
Device pulls the URL Device advertises ANNOUNCE and a media player. The Voice PE. HA sends the device the proxy URL and the device fetches it itself, in the format the device asked for. HA reads that format off the device and sets preferred_format, preferred_sample_rate, preferred_sample_channels and preferred_sample_bytes accordingly.

For the Voice PE specifically, that format is not a guess. Its own ESPHome config declares the announcement pipeline as format: FLAC, num_channels: 1, sample_rate: 48000, with the inline comment "FLAC is the least processor intensive codec". So on a Voice PE, our WAV goes through one ffmpeg hop into mono 48 kHz FLAC on the way out.

Both of these vindicate HANDOFF decision 5.6. Returning WAV is not a compromise, it is the format one path requires outright and the other transcodes from most cheaply. HA's converter even passes -probesize 32 when the live input is WAV, with the comment "The container is known, so minimize probing latency for live TTS audio." Returning MP3 would put us on the slow side of that branch for no benefit.

Wyoming and ESPHome, and which one is dying

Two transports, and the received wisdom about them is now out of date.

  • Wyoming is a small socket protocol. It is still how Piper, Whisper, openWakeWord and Speech-to-Phrase attach to HA as services, and that is not going anywhere.
  • Wyoming as a satellite transport is over. rhasspy/wyoming-satellite, the project every "build a Pi voice satellite" tutorial targets, is archived and read only. The GitHub API returns "archived": true with a last push of 2026-01-24 and 212 open issues left standing. A search snippet of the repo page puts the archive date at 2026-01-27.
  • The replacement speaks the ESPHome protocol instead. OHF-Voice/linux-voice-assistant, Apache-2.0, 618 stars, last pushed 2026-09-03, and now renamed (the hav-sat repo returns byte-identical metadata, so it is the same repo behind a rename). Its README calls itself "an experimental voice satellite software for Home Assistant remote voice control" and wants a 1 GHz CPU, 512 MB of memory and 16 kHz mono audio.

So anything you build on a Raspberry Pi should target the ESPHome protocol through Linux Voice Assistant, not Wyoming, and it lands you on "experimental" software either way. That single fact moves a Pi satellite from "the frugal choice" to "the project."

3. The cheapest way to hear Flux in your house

Three honest rungs. The first is free.

Zero dollars: the browser as the player

Media panel, Text-to-speech, pick the engine, type a sentence, and in Choose player pick Web browser. That target is real and current: the HA frontend's own translation file on dev carries "web-browser": "Web browser" in its media browser strings.

What it proves: the API key works, voice selection works, language routing picks an Aura voice for Spanish, the bytes decode, and Flux sounds the way you want on the machine you are sitting at. That covers HANDOFF verification for chapters 2 through 5 except the words "on the real instance."

What it cannot prove: there is no microphone, no wake word, and no hands-free anything. The browser is not a media_player entity, so it exercises neither the tts.speak path nor the announce path, which are exactly the two paths that break in interesting ways. And browser media buffering is not under HA's control, so any timing you take here is noise. Inferred, not measured.

$12.50: a real media_player on the Home Assistant host

Plug the Adafruit Mini External USB Stereo Speaker into the HA host. It is a USB audio class device, so no driver work. Then install the official VLC app (formerly add-on, version 1.1.0, built for aarch64 and amd64, declared audio: true). It discovers itself into the vlc_telnet integration and you get a genuine media_player entity whose output is the host's audio device. The vlc_telnet docs say it plainly: "You can run a VLC Media Player on your Home Assistant installation using the official VLC app."

You need this step because Home Assistant OS does not hand you a media_player for a locally attached speaker on its own. No official doc says so in one line, several years of community threads say so at length, and the existence of an official VLC app is the strongest evidence. Call that claim weak but well supported.

This rung is what makes tts.speak real, and it is the right place to first measure time to first audio, because the chain is short and nothing in it is trying to be clever.

What does not work, so you do not waste an evening

  • The companion app on your phone. Android TTS notifications (message: "TTS" plus tts_text) use the phone's own speech engine, not a Home Assistant TTS entity. The docs limit it to "the current Text To Speech locale set on the device." It cannot speak Flux. iOS has no equivalent at all.
  • An existing smart speaker as output only. You own none, so this is a purchase, not a shortcut. A Cast or Sonos speaker costs more than a Voice PE, gives you no microphone, and drops a buffering black box into the one measurement this project cares about.
  • Bluetooth to the HA host. Possible, miserable, and it adds a variable latency you will then have to explain on camera. Skip it.

5. The devices, with opinions

Home Assistant Voice Preview Edition. Buy it.

$58.95 at CloudFree ("239 in stock") and at ameriDroid ("In stock"), against a $69 official MSRP, all three pages checked 2026-09-15. ESP32-S3 with 16 MB flash and 8 MB octal PSRAM, dual mic array fronted by an XMOS XU316 doing echo cancellation, noise removal and auto gain, an internal speaker, and a 3.5 mm output with a dedicated DAC.

Works with our integration: yes, and by the better of the two paths. It is an assist_satellite with announce support, so it fetches our audio from the TTS proxy itself as mono 48 kHz FLAC. No PCM babysitting, no format guessing.

Mic: reviewers split. Some are happy at a normal speaking voice across a home office; at least one had to get close before the wake word landed, and everyone agrees accuracy falls off in a noisy room. Call it good to a few meters in a quiet room. All of that is reviews, so weak.

Speaker: fine for a spoken reply, thin for anything else, and reviewers call it too quiet for a kitchen. Which is what the headphone jack is for.

What it is actually good for: everything this project needs, and it is the only item on the list that looks like a product on camera rather than a dev board with wires.

ESP32-S3-BOX-3. Do not order it.

$49.95 at Adafruit and the page says Out of stock (checked 2026-09-15). Verdict: technically fine, functionally similar to the Voice PE, more expensive than the Voice PE, and I cannot give you a buy link I trust. The screen is the only argument for it and it is not worth a stock hunt.

M5Stack ATOM Echo. $13.50, and it will make your streaming work invisible.

"Regular price $13.50 USD", "10+ In Stock" on M5Stack's own store, checked 2026-09-15. SPM1423 PDM microphone, a 0.8 W speaker through an NS4168. This is the device behind Home Assistant's own "$13 voice assistant" tutorial, which is still published.

The problem is the chip. It is a classic ESP32, not an S3, so microWakeWord will not run on it and the wake word has to run server-side in Home Assistant with the openWakeWord app. That means it streams audio to HA continuously and your wake-to-response time picks up a whole extra network and inference stage that has nothing to do with us.

And it takes the PCM path, because it advertises the SPEAKER feature. HA reads our stream and pushes 16 kHz mono PCM to it, paced against a 512 ms ring buffer that the code holds at roughly 384 ms. So expect somewhere around 0.3 to 0.5 s of device-side latency before anyone hears anything. Inferred from the pacing code and its comments, not measured.

Good for: a $13 second or third room, a throwaway, proving the integration works on hardware you do not mind bricking. Bad for: any sentence in a blog post that contains the words "time to first audio". Worth knowing: the Atom EchoS3R is $14.50, "10+ In Stock", and fixes the chip (ESP32-S3-PICO with an ES8311 codec and a 1 W speaker), but I could find no Home Assistant or ESPHome page covering that specific board, so buying it is a small research project. Flagged as unverified.

A Raspberry Pi satellite. The trap, this year specifically.

The parts are cheap and in stock: Pi Zero 2 W $17.25 at PiShop.us, or $20.75 with headers pre-soldered, which you need for any HAT unless you like soldering. Add a $5.95 Adafruit Mini USB Microphone ("needs no driver") and the $12.50 USB speaker and you are at about $37 to $52.

The software underneath moved this year. Every tutorial you will find points at rhasspy/wyoming-satellite, which is archived and read only with 212 open issues left behind. The live path is OHF-Voice/linux-voice-assistant, which speaks the ESPHome protocol, is actively pushed (2026-09-03), and describes itself as experimental. It wants PulseAudio or PipeWire and 16 kHz mono in.

Verdict: the cheapest way to get a second satellite if your time is free, and the most expensive if it is not. You are debugging ALSA device names and an experimental daemon in the same week you are trying to measure a websocket. It is also the ugliest thing on this list on camera. Skip it for the demo; revisit it if you ever want a satellite in a closet.

6. What matters for a cloud streaming TTS integration

HANDOFF section 5 item 6 and chapter 6 both hang on one number: time to first audio. Hardware can make that number meaningless, and here is exactly how.

Things that destroy the measurement

ChoiceWhat it doesConfidence
Snapcast, anywhere in the chain Music Assistant's own docs: "The total buffer between the signal being read on the server and played out on the client, which is also the total latency of the audio. The default is 1000 ms." A full second, by design, adjustable from 200 to 6000 ms. Home Assistant even ships a snapcast.set_latency action. Verified, vendor docs
Music Assistant announcements For players with no native announce, MA stops the music, adjusts volume, plays the clip, then restores state. That is a serial sequence around our audio. Community reports put the visible delay at 10 to 20 seconds in some versions. Docs for the mechanism, forum threads for the numbers, so weak on magnitude
Chromecast A pychromecast issue records live streams stuck in BUFFERING for about 20 s versus about 1 s for a static MP3 URL. Old, and a single report. Weak, but the failure mode is real and structural: it wants to prebuffer
DLNA renderers Our stream has no Content-Length. HA's proxy carries a HEAD handler specifically for Samsung DLNA renderers that ask first. A renderer that insists on a size either stalls or buffers to the end. Verified from core source and its comment
The HA TTS cache Not hardware, but it will fool you first. tts.speak defaults cache: true, and the non-streaming setter is documented as using a disk cache. Say the same sentence twice and the second run measures the file system. Measure with cache: false and a fresh sentence every time. Verified from core source

Things that preserve it

  • The VLC app on the HA host. Shortest chain available: our generator, the chunked proxy, one local HTTP fetch, one audio device.
  • A Voice PE. It fetches the URL itself as FLAC and starts playing on arriving frames. One ffmpeg transcode hop on our side, which is streaming-safe. Tens of milliseconds, not hundreds. Inferred, not measured.
  • The pipeline handoff itself is early. HA emits the TTS URL to the satellite as soon as the stream token exists, not when the audio is complete, so the device can be fetching while Flux is still generating. Verified in esphome/assist_satellite.py.

What to actually instrument

Three timestamps, and keep them separate. First, the Deepgram socket's first binary frame, measured in our client. Second, the first byte we write into the TTS proxy response. Third, the wall-clock moment sound leaves a speaker, which you can only get with a microphone and a waveform. The gap between one and two is ours to defend. The gap between two and three belongs to the hardware choices in this table, and a Snapcast group will happily add a second to it and make our work invisible.

One more integration-side note that hardware forces: the socket gives raw linear16 with no container, and both playback paths are happiest with WAV, so the WAV header decision is doing real work rather than being a formality. What we do not know is the sample rate the Flux socket emits at, and that matters because one path wants 16 kHz and the other wants 48 kHz. Find it in chapter 2 and write it down.

7. What filming needs that working does not

Working means audio comes out. Filming means a viewer believes it.

  1. The device has to be in frame and has to look like a device. The Voice PE is the only thing here that reads as a product. A bare ESP32 board taped to a shelf, or a speaker hidden behind the laptop, makes the shot look staged even when it is not. If the sound comes from somewhere the viewer cannot see, they assume you pressed play.
  2. The LED ring is your edit. Wake word chime, then listening, then responding. Those transitions are visible on camera and they are natural cut points and natural proof of liveness. Shoot wide enough to keep the ring readable.
  3. Route audio out to the Pebble for the on-camera room. The internal speaker is built for voice feedback and reviewers call it too quiet for a kitchen. On a camera mic, thin and quiet becomes unusable. The 3.5 mm jack has a dedicated DAC, so this costs you nothing in quality.
  4. Pick a soft room. Carpet, curtains, a couch. A hard room gives you reverb, which hurts twice: the wake word misses more, and the recording sounds like a parking garage. Stand 1 to 2 m away, which is also where the mic array actually performs.
  5. Capture the room and the logs separately. Do not try to frame a speaker and a screen full of Home Assistant logs in one shot. Record the room take, then screen-record the Assist debug view on its own, and cut the timing numbers in as text. A phone on a tripod and a screen recorder beats a compromise wide shot.
  6. The second room is the argument. One continuous shot where you ask in the office, walk to the kitchen, ask again, and a different Flux voice answers from a different device is worth more than any latency chart. That is the one thing you cannot fake in post and the specific reason to buy two pucks rather than one.

One thing to watch: your own recording setup will hear the TTS playback. The Voice PE's XMOS chip does echo cancellation for the device's mic, not for yours. If you are also recording a voiceover in the room, record it separately.

8. Microphones, treated honestly

Our integration is text to speech. It has no microphone story at all. But nobody believes a voice assistant demo where the human types, so the bill of materials has to leave you able to talk to the thing, and that means speech to text from somewhere.

Three options, in order of how little they will cost you in time:

  1. Home Assistant Cloud. If you have a Nabu Casa subscription, STT is already configured and this is a non-decision.
  2. The Whisper app locally. Official, Wyoming-based, still maintained in home-assistant/addons. Costs CPU, costs nothing else.
  3. Deepgram STT. There is a community custom integration, Automaat/deepgram-stt, MIT licensed, Nova-3, created 2026-01-31 and pushed 2026-09-15, with 1 star and 3 open issues. It is alive but it is one person's early project. It is a useful reference and a bad dependency for a demo you are filming. Nova-3 monolingual streaming is listed at $0.0048 per minute pay as you go (regular $0.0077), checked 2026-09-15 on Deepgram's pricing page, against Flux TTS at $0.045 per 1,000 characters.

There is an obvious content argument for Deepgram on both ends of the pipeline. Take it if you want, but take it as a separate piece of work, after chapter 5 is on real hardware. Do not let it block the TTS integration.

Which hardware decisions are the microphone's, not the speaker's. This is the useful separation, because almost every dollar above Tier 1 is mic money:

  • Mic array and echo cancellation. The reason a Voice PE costs $59 and a USB mic costs $6 is the XMOS chip. Without echo cancellation, the device hears its own TTS output and retriggers or talks over itself. That is a mic requirement created by having a speaker.
  • On-device wake word. Needs an ESP32-S3. The Atom Echo's plain ESP32 cannot do it, so the wake word moves to the HA server and the room streams audio continuously.
  • Far-field range. Beamforming is what makes 4 m work instead of 1 m, and it is the whole value of the XVF3800 board.
  • The HAT driver tax. Device tree overlays, codec drivers, ALSA names. Pure mic cost, zero benefit to output.

If you only ever wanted output, Tier 1 is $12.50 and you are done. Everything above it is the price of being able to talk.

  • Raspberry Pi Zero 2 W stock. PiShop.us shows $17.25 and $20.75 with headers but no in-stock wording either way, only a one-per-customer limit.
  • ReSpeaker Lite kit stock. Seeed's page gives $26.99 and three warehouse options but no stock count.
  • Satellite1.1 HAT availability. Its page says backorder with a restock date of 2026-07-15, which is already past. I did not email them.
  • Atom EchoS3R software support. $14.50 and in stock, but no Home Assistant or ESPHome documentation for that exact board. One customer review mentions using it with HA.
  • Every latency figure that is not sourced to code. Nothing here was measured on hardware, because there is no hardware yet. The device-side buffer estimate of 0.3 to 0.5 s and the claim that a FLAC transcode costs tens of milliseconds are both inferred from reading the implementation.
  • Microphone and speaker quality judgments. All of those come from published reviews, not from me listening to anything.
  • The wyoming-satellite archive date of 2026-01-27 comes from a search snippet. The archived flag and the 2026-01-24 final push are from the GitHub API and are solid.
  • The claim that Home Assistant OS exposes no media player for local audio. Well supported by community threads and by the existence of an official VLC app, but no single authoritative statement was found.
