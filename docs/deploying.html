Getting this integration onto a real Home Assistant instance

Deepgram TTS for Home Assistant. Written 2026-09-15 against Home Assistant 2026.9.x.

HANDOFF section 6 puts a gate in front of chapter 6: the batch path has to be running on the real instance before any streaming work starts, because that is what makes the streaming work verifiable instead of theoretical. Nobody had written down how code in this repo reaches that instance. This page is that path, plus the checklist that closes the gate.

Two scripts do the work. scripts/deploy.sh copies the integration and restarts Home Assistant. scripts/tail_ha_log.sh answers the only question that matters immediately after, which is whether it loaded. Both read the same environment variables from the same gitignored env file.

Three answers are still needed before either script runs. The install type of the instance, its hostname and port, and which apps are installed on it. Nothing here guesses them. The full list is in docs/deploy-notes.md.

1. Installation methods, ranked by loop speed

The reader of this page is iterating on Python many times per hour. That makes the edit to audible speech loop the deciding factor, not elegance and not how a stranger would install the finished thing.

MethodNeeds on the HA sideSurvives an HA upgradeReload without restartLoop speed
rsync over ssh into config/custom_components/ Shell access. The SSH app, the OS host shell on 22222, or plain sshd on Container and Core Yes. The config directory is not touched by an HA update No. See section 3 Fastest. One command, seconds, only changed files move
Local copy into a bind mount Container or Core, with the config directory reachable as a path on the machine you edit on Yes No Fastest. No network at all. Needs the right topology
Samba share, drag the folder in The Samba app, so OS or Supervised only Yes No Medium. Fine by hand, awkward to script, and SMB is slow on many small files
Studio Code Server, edit in place The app, and aarch64 or amd64. Not 32 bit arm Yes No Medium. No copy step at all, but you are editing a second copy of the code that is not the git working tree
git clone on the HA host, then git pull Shell access and git on the far side, which the SSH apps do not all ship Yes No Medium. Requires pushing before every test, so every experiment becomes a commit
HACS custom repository HACS installed, and the repo reachable by GitHub URL Yes, and HACS tracks and offers updates No Slowest. A tag or a release per iteration, then a click in the HACS UI. This is the shipping path, not the dev path
Manual zip from a release Nothing beyond file access Yes, but you own every update by hand No Slow. Useful for proving the release artifact works, useless for iteration

Recommendation

Use rsync over ssh for the whole of chapters 5 and 6, and use HACS exactly twice: once at the end of chapter 7 to prove the distribution path works on a clean instance, and once after the flip to public to prove a stranger can install it. If the instance is a Container install whose config directory is a bind mount from a host you can already write to, use the local transport instead and skip SSH entirely.

The reason is not speed alone. rsync keeps the git working tree as the single source of truth. A Studio Code Server or Samba workflow tempts you into editing on the far side, and then the fix that made it work lives on the Pi and not in a commit. That failure mode is expensive precisely because the lab convention rewrites this history into build order later.

2. Every way to get a file onto a running instance

Install type decides most of this. Apps, which were called add-ons until Home Assistant 2026.2 renamed them, need the Supervisor. Container and Core have no Supervisor, so half the table below does not exist for them. That is the detail that costs an afternoon.

PathHA OSSupervisedContainerCoreNotes
Samba appYesYesNoNo Exposes config, share, ssl, backup, media, plus local_apps and app_configs, which were addons and addon_configs before the rename. Both names still work. Credentials are set in the app config and are not your HA login
Advanced SSH and Web Terminal appYesYesNoNo Public key auth is the documented recommendation over a password. It runs in a container with /config mapped, so a shell here is not a shell on the host. Alpine based, so rsync and git are not guaranteed to be present

One thing that is true on every install type: the config directory is yours, and a Home Assistant version upgrade does not remove anything from custom_components/. A custom integration surviving an upgrade is not the risk. The risk is the opposite, that an upgrade changes an API the integration used and the integration keeps sitting there failing to load. HANDOFF section 2.2 is a list of exactly that kind of breakage.

3. Reloading without restarting, honestly

A custom integration's Python cannot be reloaded in place. Python caches imported modules in sys.modules. Once custom_components.deepgram_tts.tts is imported, that object is what the process has, and rewriting the file on disk changes nothing about the running interpreter. Home Assistant does not work around this, and neither does HACS.

What the reload action actually does, quoting the Home Assistant docs for homeassistant.reload_config_entry: it "reloads an integration's config entry without restarting Home Assistant," and "reloading briefly unloads the integration, so its entities are unavailable for a moment while it sets up again." It takes an optional entry_id and can be targeted at an entity, device, area, floor, or label. It is admin only.

So it re-runs async_unload_entry and async_setup_entry against the module that is already loaded. That is genuinely useful for some things and useless for others:

ChangeWhat picks it up
An option changed in the options flowReload the config entry
A voice catalog that failed to fetch and should be retriedReload the config entry
An expired or replaced API keyReload the config entry
Any edit to a .py fileFull restart. Nothing less
A new or renamed module inside the integrationFull restart
manifest.json, including a version bumpFull restart
strings.json or translations/en.jsonFull restart. Translations are cached at load
A new entry in requirementsFull restart, and HA installs the package during startup, so that restart is slower than usual

Practical consequence for the loop: every code iteration costs one Home Assistant restart. On a Raspberry Pi that is tens of seconds, sometimes more than a minute. That cost is the argument for making the copy step instant and scripted, which is what deploy.sh is for, and for running the unit tests locally first so the restart is spent on something a test could not have caught.

There is no supported hot reload hook for a TTS entity. Do not go looking for one. Chapter 6's websocket path is where a long lived connection makes restart cost feel worse, and the answer there is still a restart.

4. scripts/deploy.sh

Every setting is an environment variable prefixed HA_DEPLOY_, documented in a block at the top of the script itself, so the script is its own reference. An optional env file is sourced first. Default location scripts/.ha-deploy.env, already added to .gitignore, override with HA_DEPLOY_ENV_FILE.

An env file for the rsync transport:

# scripts/.ha-deploy.env  (gitignored, never commit this)
HA_DEPLOY_TRANSPORT=rsync
HA_DEPLOY_SSH_HOST=REPLACE_ME
HA_DEPLOY_SSH_USER=root
HA_DEPLOY_SSH_PORT=22
HA_DEPLOY_CONFIG_DIR=/config
HA_DEPLOY_URL=http://REPLACE_ME:8123
HA_DEPLOY_TOKEN=REPLACE_ME
HA_DEPLOY_RESTART=restart

And for a bind mounted Container install, where no SSH is involved:

HA_DEPLOY_TRANSPORT=local
HA_DEPLOY_CONFIG_DIR=/Users/samgutentag/path/to/ha/config
HA_DEPLOY_URL=http://REPLACE_ME:8123
HA_DEPLOY_TOKEN=REPLACE_ME

Then:

HA_DEPLOY_DRY_RUN=1 scripts/deploy.sh    # print the plan and an rsync dry run
scripts/deploy.sh                        # copy, then restart

Behavior worth knowing before the first run:

  • HA_DEPLOY_TRANSPORT has no default. Unset, the script fails with a message naming both valid values. Guessing wrong writes files to the wrong machine, so it does not guess.
  • It refuses to run if the source has no manifest.json. That is the guard that stops a typo'd path from becoming a destructive sync on the far side.
  • It never deletes on the destination by default. rsync --delete is behind HA_DEPLOY_ALLOW_DELETE=1, and the script header says why: delete removes whatever is on the destination and absent from the source, so a wrong HA_DEPLOY_CONFIG_DIR plus delete removes somebody else's integration, with no undo. The one legitimate reason to turn it on is a renamed or removed module leaving a stale .py that Home Assistant keeps importing.
  • The source path has no trailing slash on purpose. rsync then transfers the deepgram_tts directory itself, which also scopes any --delete to that one directory rather than to everything under custom_components/.
  • The restart step is skipped cleanly with no token. No HA_DEPLOY_TOKEN means the copy still happens and the script tells you to restart yourself. Create the token on the Home Assistant profile page, at the bottom under Long Lived Access Tokens.
  • It prints the plan before acting and one summary line after. The summary is the line you read out of a scrollback: version, transport, destination, what was copied, what was restarted, elapsed seconds. The token is never printed.

A restart is POST /api/services/homeassistant/restart. There is no dedicated restart endpoint in the REST API; everything goes through POST /api/services/<domain>/<service> with an Authorization: Bearer <token> header. Setting HA_DEPLOY_RESTART=reload posts homeassistant.reload_config_entry with an HA_DEPLOY_ENTRY_ID instead, which is the right choice only for the config and catalog cases in section 3.

5. scripts/tail_ha_log.sh

Same env file, same prefix. HA_DEPLOY_LOG_SOURCE picks api or ssh and has no default, for the same reason as the transport.

HA_DEPLOY_LOG_SOURCE=api scripts/tail_ha_log.sh      # poll /api/error_log, filtered
HA_DEPLOY_LOG_SOURCE=ssh scripts/tail_ha_log.sh      # tail -F the log file over ssh
HA_DEPLOY_LOG_FOLLOW=0 scripts/tail_ha_log.sh        # one shot, print the backlog and exit
HA_DEPLOY_LOG_FILTER='.' scripts/tail_ha_log.sh      # everything, not just this integration

The default filter is deepgram_tts|deepgram|DeepgramError|tts\., which catches the integration's own logger name, its typed errors, and the TTS component's lines.

One honest limitation: GET /api/error_log returns, in the docs' words, "all errors logged during the current session of Home Assistant as a plaintext response." It is a whole document fetch, not a stream, and there is no server side tail. So the api source polls every HA_DEPLOY_LOG_INTERVAL seconds and prints what is new. A restart makes the log start over, which the script detects as the line count dropping and reports rather than silently printing nothing. The ssh source has none of that awkwardness because it is tail -F on a real file, but it needs shell access and it assumes the default logger is writing home-assistant.log into the config directory.

6. The release path

.github/workflows/release.yml runs on a v* tag push, on a published release, and on manual dispatch with a tag. It does three things:

  1. Resolves the tag for whichever event fired, since a tag push and a published release carry it in different places.
  2. Compares version in manifest.json against the tag with the leading v stripped, and fails with a ::error annotation on manifest.json when they differ. HACS reads the version from the manifest and not from the tag, so a mismatch ships a build that reports the wrong version to every user, forever.
  3. Zips the contents of custom_components/deepgram_tts/ with the files at the archive root, lists the archive so the log shows what shipped, and attaches it to the release using the gh CLI that is already on the runner. No third party action, so no new dependency in the release path.

hacs.json currently has "zip_release": false, and this work does not change that. The zip is still worth attaching, for manual installs and for anyone not running HACS. docs/deploy-notes.md records what would have to change together if that flag ever flips, which is a filename key in hacs.json, an exact match between that name and the asset name, and a guarantee that every future release carries the asset.

7. Real hardware checklist

This closes the chapter 5 gate from HANDOFF section 6.1. Work down it, one box at a time. Do not start chapter 6 with an unchecked box above this line.

Before the first deploy

  • Answer the three questions in docs/deploy-notes.md: install type, hostname and port, which apps are installed.
  • Create a long lived access token at <ha-url>/profile, bottom of the page, and put it in scripts/.ha-deploy.env.
  • Confirm the env file is ignored: git check-ignore -v scripts/.ha-deploy.env prints a rule.
  • Confirm the API answers at all: curl -H "Authorization: Bearer $TOKEN" $URL/api/ | grep -i running.
  • Run HA_DEPLOY_DRY_RUN=1 scripts/deploy.sh and read the plan. Confirm the destination path is the one you meant.
  • Tests green locally first: .venv/bin/pytest -q. Every restart is tens of seconds, so do not spend one on something a test would have caught.

Deploy and confirm it loaded

  • scripts/deploy.sh. Read the summary line. Copy happened, restart requested, no error.
  • HA_DEPLOY_LOG_SOURCE=api scripts/tail_ha_log.sh in a second terminal, through the restart.
  • No Error while setting up deepgram_tts platform, no Unable to prepare setup for platform, no ModuleNotFoundError, no Setup failed for custom integration in the log. A traceback naming a package we did not declare is the exact failure from HANDOFF section 2.1, so read it rather than retrying.
  • Settings, Devices and services shows Deepgram TTS with no error card, and an entry titled for the chosen voice.
  • Developer Tools, States has a tts. entity for it. Write down its entity id. The YAML below needs it, and it is derived from the entry title so it is not guessable from this page.

Confirm flux-haley-en is the default on a fresh install

  • Do this on an entry added after this deploy, not on one carried over. A pre-existing entry has a stored voice and proves nothing about the default.
  • Add the integration fresh. The voice step's preselected value is Haley, and the entry title reads Deepgram Flux (Haley).
  • Confirm it against the stored data rather than the UI label: Developer Tools, Template, render {{ state_attr('tts.YOUR_ENTITY', 'friendly_name') }}, and separately check the entry's options in the UI show voice flux-haley-en.
  • Sanity check the reason it is the default: flux-marcus-en and flux-brittany-en drift in pitch and volume between calls and can click at clip starts, which a house full of short separate calls makes audible. Both are cleared for use and belong in the picker. Neither should be preselected.

Confirm tts.speak produces audio

  • Paste this into Developer Tools, Actions, YAML mode, and run it. Replace both ids with real ones from Developer Tools, States.
action: tts.speak
target:
  entity_id: tts.REPLACE_ME
data:
  media_player_entity_id: media_player.REPLACE_ME
  message: "Your appointment is confirmed for 3pm tomorrow."
  cache: false
  • Audio actually comes out of the speaker. Not just an action that returned without raising.
  • cache: false stayed in the call. With caching on, the second run answers from disk and you stop testing the integration.
  • The log shows one request and no traceback. No repeated retry, no DeepgramAuthError, no DeepgramConnectionError.
  • Run the same call a second time and confirm it is not slower than the first in a way that suggests a per-call catalog fetch.
  • Run it through the Assist pipeline too, not only the direct action. HANDOFF section 2.1 is the record of a bug that broke every pipeline response while direct tts.speak kept working, so testing one does not test the other.

Confirm a Spanish pipeline resolves Aura and not Flux

Every Flux voice is English. A Spanish request resolving to a Flux voice is the single most likely correctness bug in chapter 5, and it will not raise. It will just speak Spanish words in an English voice, which sounds wrong and is easy to talk yourself out of hearing.

  • Turn on debug logging for the integration first, so the resolved voice id is in the log rather than inferred from the audio. In configuration.yaml, then restart:
logger:
  default: warning
  logs:
    custom_components.deepgram_tts: debug
  • If chapter 5 does not log the resolved voice id, add one debug line that does, in tts.py, and deploy again. Confirming this by ear is not confirming it.
  • Run the Spanish call:
action: tts.speak
target:
  entity_id: tts.REPLACE_ME
data:
  media_player_entity_id: media_player.REPLACE_ME
  language: es
  cache: false
  message: "Tu cita esta confirmada para manana a las tres de la tarde."
  • The log line names an aura-2- or aura- model. Anything starting flux- is the bug.
  • The audio is a Spanish voice, not an American English voice reading Spanish.
  • Repeat with language: de. Same expectation. Two languages confirms the routing rule, one confirms a coincidence.
  • Check the language dropdown in the entity's options shows base codes only. A list mixing en and en-US is the split("_") bug from HANDOFF section 2.2 come back.

Capture the evidence

This is the part that gets skipped and then wanted three weeks later, when the build log post needs a real log line and not a paraphrase. scripts/out/ is already gitignored, so it is the place to put all of it.

  • Record the four numbers that date the run: Home Assistant version from Settings, About; the integration version from manifest.json; the install type; and the git SHA you deployed, git rev-parse --short HEAD.
  • Save the whole log from the run, not just the lines you liked: curl -H "Authorization: Bearer $TOKEN" "$URL/api/error_log" > scripts/out/error-log-$(date +%Y%m%d-%H%M).txt
  • Save the two audio files. A direct call to /v2/speak with the same text gives you a reference clip next to what Home Assistant played.
  • Screenshot the successful tts.speak action in Developer Tools, and the integration card with no error on it. Screenshots age better than remembered outcomes.
  • Screenshot the voice picker on a fresh add, showing Haley preselected. That one image is the whole default-voice claim.
  • Write what surprised you into .hub/ledger.md, while you still remember the symptom you saw before you knew the cause. The ledger is append-only and exists for exactly the facts a later repo scan cannot recover.
  • Note the wall clock time from action to first audible sound. It is not a real latency measurement and should not be published as one, but it is the baseline chapter 6 has to beat, and HANDOFF section 7 already flags first-frame latency as unmeasured.

Gate

  • Every box above is checked, and chapter 6 can start.
  • Do not start /advocacy-intake yet. HANDOFF section 8.5 puts that after chapter 5 is on real hardware, and the honest claim is not ready until this checklist is done and the streaming work has a result.

8. What is still unanswered

Short list, kept in full in docs/deploy-notes.md.

  1. The install type, hostname and port, and installed apps of the instance. Three answers, thirty seconds, and both scripts are configured.
  2. Whether the config directory is a bind mount this laptop can write to. If yes, the local transport is faster than everything else here.
  3. Whether the far side has rsync. The official SSH apps are Alpine based and do not all ship it, and its absence fails at the remote end in a way that reads like a key problem.
  4. Whether a home-assistant.log file exists on disk. The ssh log source assumes it; the api source does not care.
  5. shellcheck is not installed on this machine, so both scripts were verified with bash -n only. Worth one shellcheck run before the flip to public.
